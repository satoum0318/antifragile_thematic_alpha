## 実装した範囲

| 対象 | 動作 |
|---|---|
| 通常 `collect` | 日付による取得停止を解除し、同じ `/v2/markets/margin-interest` を検証アダプタへ通す。従来の価格日固定・収集対象選択は保持。 |
| `margin_refresh` | 指定した通常snapshotの普通株を、完了銘柄も含め信用残だけ再取得。通常snapshotを更新せず、独立したsnapshot・再開記録へ保存。 |
| `margin_analyze` | 保存済み信用snapshotと元の価格snapshotだけを読み、通信・認証情報読込・再採点をせず専用診断を出力。 |
| 通常 `analyze_symbol` | 同じ診断定義を使用。通常snapshot内の信用残と通常分析の情報締切だけを使用。専用信用snapshotを暗黙に混ぜない。 |
| メニュー・ランナー | メニュー10で信用残更新、11で信用診断。ランナーも両フェーズに対応。 |

信用残は安全性点・投機性点・旧参考点・推奨点・新規買い可否へ接続していません。`short_selling_change_rate` は従来の空欄を維持します。`update_daily`、価格の日次進行、規制の空売り残高報告、日々公表銘柄の取得仕様は変更対象外です。

責務は `jq_margin.py`（純粋な検証・診断計算）、`jq_margin_workflow.py`（専用収集・履歴・出力）、`JQuamtsScreeningBot.py`（CLIと通常処理への接続）に分かれます。

## 操作

Python 3.10以上、`numpy pandas requests` を使用します。通常snapshotがある既存キャッシュを指定してください。信用残更新は価格や財務データを用意する機能ではありません。

### 新Botの起動とランキング最大10件の出力

PowerShellでリポジトリ直下から起動します。実際のファイル名は `JQuamtsScreeningBot.py` です。

```powershell
Set-Location C:\project\antifragile_thematic_alpha
python -B .\JQuamtsScreeningBot.py --version
python -B .\JQuamtsScreeningBot.py --top 10
```

版表示は `1.1.0-rc2-margin-daily / JQ-STD-CORRECTED-1.0-rc1` です。起動後は次のメニューを使います。

- **4：日付単位で差分更新** — 保存済み銘柄の価格・財務等を更新。価格基準日が古い場合は、まず更新が成功したことを確認します。
- **2：オフライン一括分析** — 保存済みデータで採点し、条件を満たす候補を最大10件出力。
- **10：信用残だけを更新、11：信用残の診断** — 日次信用残を別途確認。価格基準日やランキングを更新する操作ではありません。

初回で通常の収集履歴がない場合は、先にメニュー1で収集します。未取得や打切り失敗が残る場合、その状態は解消済みと扱いません。

ランキングは `output_standard/reports/latest/top_recommended_core.csv`、説明は同じ場所の `report_core_top10.md` です。`eligible_new_entry=true` の候補だけを対象とし、10件に満たない場合は該当件数だけを出します。確認用の `run_manifest.json` に価格基準日・情報締切・実行状態、`filter_summary.json` に適格件数・除外理由があります。

直接コマンドで実行する場合は、`--phase update` で日付更新後、`--phase analyze --top 10` で分析します。更新はAPI通信を行い、分析は通信しません。`runner.py` の既定は20件なので、ランナーでも10件を希望する場合は `python runner.py --phase analyze --top 10` と明示します。

今回の第1段階で日次信用残は採点へ接続していません。テストは処理と既存採点の不変性を検証したもので、投資収益や順位の予測精度を検証したものではありません。現在の候補として読む際は、価格基準日・母集団の収集状況を確認してください。

### 信用残だけの更新・診断

メニュー10は買残・売残を同じAPI応答で取得します。`LongVol` は信用買残、`ShrtVol` は信用売残です。一般・制度別の株数、日次の金額原値、買残・売残それぞれの1/5/20営業日変化も保存・診断対象です。

rc2では `report_margin.md` に買残株数と売残株数を併記し、買残・売残の5/20営業日変化を別表で出します。rc1でも買残はCSV/JSONに入っています。rc1で収集中の場合はその処理を継続でき、終了後にBotを再起動してメニュー11を実行すると、保存済み信用snapshotから新しい表示のレポートを作れます。表示変更のための信用残再取得は不要です。

```powershell
# コード版を確認
python -B .\JQuamtsScreeningBot.py --version

# 保存済み通常snapshotの全普通株について信用残だけを更新（通信あり）
python -B .\JQuamtsScreeningBot.py --phase margin_refresh

# 最新の信用残取得試行から診断を出力（通信なし）
python -B .\JQuamtsScreeningBot.py --phase margin_analyze
```

小さい範囲で動作確認する場合は対象コードと元snapshotを固定します。次のIDは自分の保存済みIDへ置き換えます。

```powershell
python -B .\JQuamtsScreeningBot.py --phase margin_refresh --snapshot-id SOURCE_ID --code 8697 --budget 1 --once
python -B .\JQuamtsScreeningBot.py --phase margin_analyze --margin-snapshot-id MARGIN_ID
```

`--cache-dir` と `--output-dir` は通常処理と共通です。既定値は `.jquants_cache_v2_standard` と `output_standard`。`--snapshot-id` は元の通常snapshot、`--margin-snapshot-id` は信用残専用snapshotで、用途を分けています。

`runner.py --phase margin_refresh` / `margin_analyze` でも起動できます。ランナーの通常既定動作はオフライン分析です。存在しなかった `DEFAULT_COLLECT_BUDGET` への参照を修正し、チェックポイントの既定値はBot設定へ委ねています。

## 取得窓、停止、再開

新しい信用収集ジョブの開始日をJSTで D とし、両端込み90暦日 `[D-89, D]` を固定します。例：9月30日開始なら7月3日〜9月30日。価格基準日を取得窓の上端にしません。`code + from + to` で全ページを取得し、`published_date` を併用しません。

通常snapshotのカレンダーで必要期間が不足するときだけ、診断用カレンダーを追加取得します。株価・財務・空売り報告は再取得しません。APIレート制御と収集ロックは通常収集と共有します。

`--budget` は1チェックポイントの銘柄数、`--once` は1チェックポイントで停止、`--max-batches` は回数上限です。指定がなければ未処理キューが空になるまで継続します。銘柄取得失敗は `--max-retries`（既定3）で打ち切り、失敗だけの再試行前は `--retry-delay`（既定60秒）待ちます。

rc2では準備開始時、対象確定時、最初の銘柄・20件ごと・最後の銘柄、チェックポイント終了時に進捗を表示します。処理中も30秒間隔でハートビートを出し、API応答・レート制限待ちの間も取得完了数／全対象数、未処理数、今回試行・失敗数、処理中コード、処理段階、今回の経過秒数を確認できます。ハートビートはプロセスが動いていることの表示で、API取得成功の保証ではありません。取得完了数には正常0行の銘柄も含みます。

ハートビートを出す補助スレッドはログ専用で、API・キャッシュ・再試行状態へアクセスしません。成功・エラー・Ctrl+Cのいずれでも停止します。すでに動いているrc1プロセスには変更が反映されないため、反映は終了後の再起動になります。途中で再起動する場合はCtrl+Cで保存・終了した後、同じ設定と保存先でメニュー10から再開できます。

Ctrl+Cでは途中状態も独立snapshotへ保存します。同じコマンドで未処理分を再開します。再開中に日付や通常の最新snapshotが変わっても、元snapshotと取得窓を保持します。取得元・対象銘柄・再試行上限を変更する場合は `--reset-pending` で新しいジョブを始めます。既存の履歴は削除しません。

正常な0行は `no_rows` として取得完了、通信失敗・権限不足・スキーマ不一致は別状態です。未処理・打切り失敗・カレンダー不足があれば更新CLI終了コード2、致命的エラーは1、中断は130です。診断CLIはレポートの作成成功を0で返し、データ不足はレポート内の状態・空欄理由で示します。最新参照先は「最新の試行」であり、今回失敗した銘柄を前回成功値で埋めません。前回観測は別欄で示します。

## 保存形式と確認する時点

```text
<cache>/objects/<hash>.json.gz       原データとアダプタ付加情報（既存形式）
<cache>/margin_snapshots/<id>.json   変更不可の信用専用snapshot
<cache>/latest_margin_snapshot.json 最新の試行への参照
<cache>/margin_collection_resume.json 信用収集専用の再開状態
<output>/margin_history/<id>/
    manifest.json
    margin_diagnostics.csv
    margin_diagnostics.json
    report_margin.md
<output>/latest_margin_run.json     最新の信用診断への参照
```

元snapshot・通常の `latest_snapshot.json`・通常の再開記録・通常の採点出力を変更しません。原レスポンス、未知の追加列、行内容ハッシュ、各版の `first_observed_at` と再観測時刻を保持します。日付が同じでも値が訂正されれば別版です。再取得した過去行に、以前の別内容の取得時刻を流用しません。

診断には元の `source_snapshot_id`、`price_asof_date`、`source_information_cutoff` と、信用診断自身の `information_cutoff` を保存します。申込日 `Date` は営業日であること、日次は `Date < PubDate <= 情報締切の日付`、採用する内容版の初回観測は情報締切以前であることを要求します。

公表時刻が日付しかない行を、公表日の午前0時から知っていたことにはしません。同じ公表日の取得後なら、その保存済み取得証拠により使用できます。週次は公表日不明のまま実際の取得証拠を使います。保存した版より前の過去順位を正確に再現できるとは扱いません。締切を指定する場合は信用snapshotの検証時刻以前に限ります。

価格が9月11日でも、9月25日以降の信用残を現在の診断として表示できます。その場合 `margin_after_price_asof=true` として時点の差を明示します。9月11日時点の順位へ後から流用しません。

## 診断値と空欄

| 主な列 | 定義・制限 |
|---|---|
| `margin_ratio` / `margin_ratio_state` | `LongVol / ShrtVol`。売残0・買残ありは `zero_short_balance`、両方0は `both_zero`、倍率は空欄。 |
| `margin_long` / `margin_short` | 信用買残株数・信用売残株数。報告件数や報告主体の合計で代用しない。 |
| `margin_short_neg` / `margin_short_std` | 一般・制度の信用売残株数。 |
| `margin_general_short_pct` | `100 * ShrtNegVol / ShrtVol`。分母0や一般売残が合計を超える場合は空欄。 |
| `margin_*_value` / `margin_value_ratio` | 金額6列の原値と金額比。単位未確認。円換算や評価価格の推定はしない。金額比は監査用。 |
| `margin_{long,short}_change_{1,5,20}bd_pct` | 対象期間の株数変化率。日次の連続 N+1 観測、同一銘柄・同一対象区分、営業日完全性、取得時点、企業行動確認を要求。 |
| `margin_short_to_volume_20bd` | 申込日までの20営業日の平均出来高に対する信用売残。実際の返済日数・公式回転日数ではない。古い価格日の出来高で代用しない。 |
| `margin_application_age_bd` / `margin_publication_age_days` | 申込日からの営業日経過と、公表日からの暦日経過。カレンダー不明なら営業日経過は空欄。 |
| `margin_bridge_*` | 最終観測週次→初日日次の別指標。始終日と実営業日数を併記し、1営業日変化へ混入させない。 |
| `margin_metric_states` / `margin_metric_reasons` | 各数値の可否と空欄理由。CSVではJSON文字列、JSONでは辞書。 |

欠測を安全や0と扱いません。取得状態、行の検証状態、対象区分、指標ごとの理由を分離します。`IssType=3` は適用対象外、未知区分は未確認です。最新行の問題を古い正常行で隠しません。適用対象外の原値は生データに残し、評価用数値を空欄にします。

株数は遡及調整済みとみなしません。既存価格キャッシュの対象期間について `ExRT`・`AdjFactor` を確認し、分割・併合・ライツ、未知の係数や確認不足があれば変化率は空欄です。価格日が古ければ新しい期間の企業行動は未確認となります。第1段階では追加株価収集や信用残の調整系列を作りません。

9月18日週次→9月25日日次は2営業日分であり、1ステップの1営業日変化ではありません。5営業日変化は最短10月2日申込分（通常10月5日公表）、20営業日は最短10月26日申込分（通常10月27日公表）。それ以前の空欄は正常です。その日以後も価格履歴・企業行動等の条件が欠ければ空欄を維持します。

### 確定した役割分担

**スクリーナーがTop10と根拠を提示 → ユーザーが自分の意思で銘柄を選定 → ユーザーがTradingBotのユニバースへ登録 → TradingBotが既存の条件で売買する。**

- スクリーナーは銘柄選定の資料を作る。Top10を無条件で全件買う一覧とは扱わない。
- ユーザーが登録する銘柄・時期を決める。候補ファイルの自動読込、ユニバース設定の自動更新、注文API連携はこの計画に含めない。
- 資金配分はユーザー自身が管理する。モメンタムに「この運用へ充てる資金の約10%」という意向は候補設計の参考情報であり、スクリーナーによる配分計算・数量提案・比率監視・リバランスは行わない。候補件数や順位も9対1へ機械的に配分しない。
- TradingBotが日足状態、5分足、余力、建玉、注文状態、ストップ、再エントリーを管理する。スクリーナーの順位落ちは売却指示にしない。
- 6〜12か月・1〜3年は候補評価の期間。TradingBotの日足EXITや場中STOPによる、それより早い決済を妨げる最低保有期間ではない。

### 追加合意：割安成長Aと高成長・信用売残B

2026-09-30のユーザー回答で、以下の目的を確認しました。これは次版の設計方針であり、現行コードへの実装完了や、数値閾値・配点の確定を意味しません。

| 枠 | 選びたい企業 | 需給の役割 |
|---|---|---|
| A：割安・財務良好・成長 | 主軸。割安性と財務品質に加え、今後の成長を検討できる根拠がある企業。安いだけで成長根拠がない企業を自動的に上位へ置かない。 | 好材料と注意材料を併記し、極端な悪化を見落とさない。信用売残が多いこと自体は必須にしない。 |
| B：高成長・信用売残 | 別枠。高いバリュエーションでも成長力を検討でき、信用売残の積み上がりが確認できるスイング候補。 | 売残の水準・変化を選定根拠に含める。成長、業績、価格・出来高と組み合わせて判断する。 |

Aを主画面、Bを別の候補一覧とする設計案です。両者を同じ点数で混ぜず、BをAの点数不足・データ不足の救済先にしません。表示件数は各枠最大10件を案としますが、件数配分・重複銘柄の扱いは未確定です。いずれも不足を不適格銘柄で埋めません。Bの独立表示は合意済み、個別の画面・ファイル構成は設計案です。資金配分・採用数の管理は本人が行います。

#### 運用スタイルとスクリーナーの担当範囲

主軸は6〜12か月、補助は1〜3年を見据え、短期の売買回数を増やさず、利益を伸ばして適切な出口で決済する運用です。「安心安全」は、財務の裏付け、極端な需給悪化への注意、理由とデータの見通しやすさを重視する設計目標として扱い、損失がないことや常に含み益であることを意味しません。

ユーザーは運用資金の約10%をモメンタムに充てる意向ですが、その管理は本人が行うと明言しました。スクリーナーが担当するのは候補の発見・比較・根拠表示です。A・Bは企業の選定基準、主軸・モメンタムは本人の運用目的として区別します。Bはモメンタム候補を探す主な入口とする案であり、Bの全件を自動的に10%枠へ登録しません。

モメンタムも日をまたぐスイングを目的とし、日中の短い値動きや売買回数の多さを評価目標にしません。日足ベースの上昇持続性、TOPIX相対、出来高の持続性、過熱・変動性を信用残と並べる案です。Aの順位も短期の需給変動だけで大きく入れ替える設計を目指しません。毎日評価を更新することと、毎日保有銘柄を入れ替えることは別であり、順位落ちは売却指示にしません。

添付のTradingBotには日足EXITと場中STOPがあり、短期・同日の決済も起こり得ます。日計りを目的としないことから、当日売却禁止や最低保有日数を追加しません。含み益追随の利確機構や目標利益での売却が実装済みとは資料から確認できないため、「適切な時期の利確」が現行Botで実現するかは未確認です。出口理由別の保有期間・損益、STOP後の再エントリー、売買回転を確認する項目として記録し、今回のスクリーナー計画では外部Botの出口・STOP・数量を変更しません。

#### 両枠に必要な成長根拠

- 比較可能な売上・営業利益の実績、売上CAGR、利益率、営業キャッシュフローと、会社予想の対象年度・公表日を分けて確認します。過去の増益と将来の増益予想を同じ観測として数えません。
- 成長の根拠には出典・期間・公表日を付けます。会社予想は実績でも保証でもなく、同一年度の予想修正と前期実績比の増益も別指標です。
- 一過性利益、赤字からの黒字転換、株数変更、変則決算で成長率が歪む場合は通常の成長率と区別します。低PERや高い代理EPS成長率だけで成長を認定しません。
- 成長根拠は「確認できる／反証がある／材料が混在／不足」を区別する設計案です。判定の数値条件・実績と予想の組み合わせは未確定で、不足を「成長ゼロ」や「成長あり」へ変換しません。
- 現行で再利用できるのは `sales_cagr`、`op_income_yoy_pct`、`op_margin_change_yoy`、`forward_np_change`、`positive_cfo_years_3y` 等です。売上CAGRには比較可能な4期が必要です。`guidance` は対象期間が一致する過去の純利益予想があれば `forecast_revision_rate` を計算します。ただし、会社予想の売上・営業利益への展開、修正履歴の持続性評価、これらを新しい成長条件へ接続する処理は追加設計です。既存指標も比較元の期間・値と開示履歴を監査して再利用します。
- 財務健全性と利益・キャッシュフローの確認は両枠で行います。Bで赤字企業や流動性不足まで許容することは今回合意していません。初期案は既存の財務・流動性の条件を出発点にし、変更箇所を個別に示します。

Aは現行のPS・業種比PS・PER等を割安性評価の出発点にします。ただし、現行FEへ少額の成長加点を足すだけで今回の要望を満たしたとは扱いません。「割安でも成長根拠なし」を本命にしない候補条件が必要です。BはAのPS・PER上限を超える企業も検討対象とし、成長と財務品質、評価水準の負担を別基準で評価する案です。高評価の許容上限や成長率との対応は未確定で、PS・PER条件を無制限に撤廃しません。

#### 需給をどう読むか

データ契約は [J-Quants信用取引残高仕様](https://jpx-jquants.com/ja/spec/mkt-margin-int) を2026-09-30に再確認しました。ここでの売残は `ShrtVol`、買残は `LongVol` です。規制の空売り残高報告の件数・主体合計を代用品にせず、市場全体の空売りが網羅されるとも表示しません。信用残の集計値だけでは、売り手の動機や実際の買戻し時期は判定できません。

| 観測項目 | 読み方と制約 |
|---|---|
| 売残・買残の水準 | 株数だけで企業間を比較せず、各残高を20営業日平均出来高で割る案。売残対出来高は実装済み、買残対出来高は追加案。実際の買戻し・売却に要する日数の予測ではない。 |
| 5・20営業日の変化 | 「多く残っている」と「最近積み増されている」を区別する。率だけでなく株数の差分も併記する案。基準残高ゼロからの増加は通常の増加率にしない。 |
| 信用倍率・一般／制度別 | 買残と売残の構成を補足する。低倍率を単独で好材料にせず、売残ゼロを低い有限倍率へ置換しない。 |
| 価格・出来高・業績との組み合わせ | 以下の例は検証する仮説。信用残だけで上昇・下落を予測しない。 |

好材料候補として観察する例は「業績に成長根拠があり、株価が崩れず、売残が多く残る／増える」「買残が減る間も株価が安定している」などです。注意材料候補は「買残が積み上がる一方で株価・出来高が弱い」「売残増加と業績悪化・下方修正・株価下落が同時に見られる」などです。これらは自動加点・減点の採用済み規則ではなく、検証対象として理由付きで並べます。観測できない悪材料や売り手の意図を補完せず、踏み上げの発生・時期を断定しません。

「高水準」「極端な悪化」の絶対値・同業比較・自己履歴比較の閾値は未確定です。旧安全性点・投機性点の増減率閾値を日次5・20営業日系列にそのまま使いません。銘柄横断比較では母集団と有効件数を固定し、自己履歴比較は日次履歴が十分になるまで未評価とします。

欠測は枠ごとに扱いを分けます。Aは信用欠測だけで企業の財務・成長を否定せず、「需給未評価」として安全加点をしません。Bは信用売残が選定根拠なので、水準・積み上がりの必要な観測が不足する場合は「信用条件の確認待ち」とし、条件成立済みB候補へ入れません。実測ゼロ、行なし、取得失敗、古い値、株数比較不能を別の理由として残します。

5・20営業日変化は、既存の日次データ・営業日窓・株数変更・公表時点の検査を満たした場合のみ採用します。期間不足は正常な欠測です。価格日と信用申込日・公表日・情報締切を整合させてから組み合わせ、9月11日の価格と9月末の信用残だけで「足元の需給良好」と判定しません。同期した価格が不足する場合は需給とチャートの複合判定を保留します。

#### 新ランキングの判定順と未決事項

設計する順序は「データと対象の確認 → 財務・流動性・重大リスクの確認 → 成長根拠 → Aの割安性／Bの高成長と信用売残 → 価格局面と需給の好材料・注意材料 → 各枠内の順位と選定理由」です。高い点数で重大リスクや必須条件の不足を相殺しません。上昇継続・転換・底固め・条件待ちを表示しますが、外部BotのLONG状態や注文許可は生成しません。

次の項目は追加の実装設計・検証が必要です。今回は仕様方針の記録のみとし、未決値を仮置きして本番順位を変えません。

| 未決事項 | 決まるまで進められる範囲 |
|---|---|
| Aの成長根拠成立条件、Bの高成長基準、実績と会社予想の組み合わせ | 元指標と公表日・比較可能性の出力、欠測と反証の区別まで進める。正式な新候補判定は保留。 |
| Aの割安基準の調整、Bの評価水準の許容範囲と財務条件 | 現行条件を比較基準として表示する。Bの高評価許容を財務不合格の救済にしない。 |
| Bの売残条件、A・B共通の需給好材料／極端悪化の閾値・除外の要否 | 水準・変化・価格の併記と分布調査まで進め、検証前の点数接続や自動除外はしない。 |
| 下降・過熱・決算前・市場全体の悪化を登録候補でどう扱うか | 現行の制約理由をそのまま併記し、対象拡張を理由に保留を消さない。 |
| A・B各枠の順位式、件数、重複処理 | 旧Top10を保存し、A・B候補の診断表を別表示する。尺度を混ぜた総合順位は作らない。 |

受け入れ観点は、(1)低PS・低PERだけの停滞企業がAの成長条件を自動通過しない、(2)成長根拠と有効な信用売残を確認した高評価企業をBで独立評価できる、(3)売残増だけの業績悪化企業が好材料扱いされない、(4)Aの信用欠測は未評価、Bの必要信用データ欠測は確認待ち、(5)上昇継続企業を直近クロスなしだけで除外しない、(6)旧Top10と新候補の判定理由を比較できる、です。数値判定の受け入れ条件は閾値確定後に追加します。

### 検証と導入の順序

1. **入力の監査**：価格基準日・情報締切・財務未取得銘柄・信用残の公表日と初回観測を確認する。価格が9月11日のままなら、信用だけ新しくても最新価格の投資判断とは扱わない。
2. **A・Bと三側面の診断案**：既存順位を比較基準に保ち、Aの割安・品質・成長、Bの高成長・信用売残について、本人が選べるよう根拠・時点・欠測を併記する出力を設計する。補助的な1〜3年評価には複数年の業績・CFO等を別欄にする。ユニバースへの登録は本人が行う。
3. **選定と執行を別記録にする**：スクリーナーの候補全体、本人が選んだ銘柄・選定日、TradingBotの実約定を区別する。本人の選択や売買タイミングの効果を、すべてスクリーナーの成績に帰属させない。両Botの自動同期は作らない。
4. **期間別の評価**：6／12か月、1／2／3年の固定期間後評価と、日足EXIT／場中STOPを含む実保有期間・損益を別集計する。実執行を評価する場合は5分足、実約定、費用、STOPと再エントリーの記録を使う。日足だけの簡略モデルは別表示にする。まだ満期に達していない観測を完了取引に混ぜない。
5. **信用指標の追加効果**：保存した当時版を使える範囲で、信用なし・ありを同じ入口／出口・費用で比較する。2026年9月開始の日次系列を過去数年に引き延ばさない。現時点では日次信用を用いた6〜12か月／1〜3年の実績検証は期間不足であり、前方観測を続ける。
6. **別バージョンで採否判断**：A・Bの成長条件・候補範囲・順位式を定義し、期間外検証とデータ監査を経て採用する。信用を候補条件や順位へ接続する影響はA・B別に確認する。旧版と現行Top10を再現可能に維持する。TradingBotの保有・決済ルール変更、ユニバース自動反映、発注連携はこの計画に含めない。

判定指標は候補数・欠測率に加え、期間別の中央値リターン、TOPIX相対、最大下落、順位の入れ替わり、費用控除後損益、業種集中を候補とします。実売買の記録を評価する場合は、出口理由別の保有日数・STOP率・再エントリー回数・売買回転も確認します。主軸とモメンタムを分けて集計し、売買回数の増加を改善とみなしません。仕様に合うことと、投資成績が良いことを別に検証します。
